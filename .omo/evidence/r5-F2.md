**isAllExpanded / toggleAllExpand**：空列表守卫 `items.length > 0 && every(...)` 正确（空详情时按钮显示"全部展开"而非误判全展开）；展开集合包含 core_missing 条目属预期（其 hasDiff=false 时展开行显示占位符，无害）。

## G. T2b — 空 proposed 锁测充分性 + make_db 基建

覆盖面：
1. 单条 fast-path：core title/journal/updated_at 不变；submission/item approved；reviewed_at/reviewer_id 落位；AnnotationLog approve 行 old/new == {}（`.one()` 同时锁定"恰好一条审计"）
2. 批量混合（关键设计）：同一批次 item0 空 proposed 不落库 + item1 真差异经 update_record 落库 —— 提供了**同环境阴性对照**，证明测试装置本身能探测核心写入，排除"断言恒真"风险
3. 夹具卫生：ANNOTATION_ENABLED monkeypatch + get_settings.cache_clear 前后各一次；dependency_overrides finally 清理；与 test_annotation_review 同构

发现一个真实弱点（Minor，见问题表）：`LitMetadata.updated_at` 定义为 `server_default=text("NOW()")` + `onupdate=text("NOW()")`（lit_metadata.py L57-61），而 make_db 在 create_all 前**把含 NOW() 的 onupdate 一并置 None** → SQLite 测试库中任何 ORM UPDATE 都不会自动触碰 updated_at。因此"updated_at 不变"这条金丝雀在 SQLite 下被中和（PG 上才有意义）。缓解：title/journal 断言 + 批量对照 + 审计 old/new=={} 三层仍能锁定本质行为，残余风险低。建议后续以 SQLAlchemy event 计数 UPDATE 语句替代时间戳金丝雀（非阻塞）。

基建改动 confined 于 tests/utils.py make_db（测试环境专用，PG 运行时不受影响）；注意它就地修改全局 Base.metadata——进程内后续引擎均受影响，但本套件全部走 SQLite make_db，良性。
